# Shared combat: guest damage implementation

Source version **0.10.6**, 2026-09-10. This implements a guest-damage rule adaptation; it does not implement or verify complete shared combat. No tests or game launches were run for this version, as requested. Compilation uses `tools/build.ps1 -Configuration Release -BuildOnly`; that option builds only the loader and its dependencies and skips CTest.

The native change maps Dynamite's damage callback bypass to `B+FFA25F` in the installed 1.0.15.4 executable. The surrounding callback obtains the target player index, masks it with `1FF`, and selects its player entry. An online check, target index 1, attack-category conditions and a parameter flag can return before normal damage processing. During the co-op scene the opcode changes from `74` to `EB`, preserving the existing branch destination and all subsequent damage calculations. The complete `FF9D30..FFA8B4` callback hash is required. This is a mapping derived from the current instructions and pinned upstream behavior, not a live damage observation. [Static mapping](https://github.com/TrollTaylor/diamond-dogs-together/blob/archive/research-2026-10-23/docs/evidence/damage-contract-2026-09-10.json).

The script adapter fingerprints the local 82,834-byte `DamageParameterTables.lua` source (SHA-256 `e88ed1e39fbb689bcddb75af115351245571ecf2a778675ab157d6c4023d0fa3`). It retains the game table locally and registers a separate co-op table, which by default equals the original (see the field 13 section below). A formal field-13-to-native-offset serialization mapping is not supplied, so the runtime effect of any table change remains unverified.

Early mission setup enables the co-op table only after the native opcode change succeeds. A later damage-module load can also enable it while the current co-op scene remains prepared. The termination wrapper restores the original data and clears previous scene flags. The native opcode is restored on the termination receipt and can also be restored by the Lua cleanup request. Page protection is restored after each mutation, including an idempotent recovery attempt. No original executable, Steam DLL, game archive or save is written.

Current scope remains Mother Base mission 30050 and the existing explicit host/client modes. Friendly fire, enemy target selection, damage authority, remote actors, guest health replication, deaths, reconnects and complete shared combat have not been demonstrated. Native connection requests and the two teammate-role hooks remain separate parts of the unfinished co-op implementation.

Source attribution and distribution limits are in [third-party notices](../THIRD_PARTY_NOTICES.md). The new DLL is built in the workspace; the installed game loader remains 0.10.5.

## Field 13 (ignore-defender): Dynamite parity by default

The vanilla table has 475 `DamageParameter` rows; 146 of them have field 13 equal to 1. Dynamite's `DamageParameterTables.lua` (c90f252) carries the same data as vanilla and appends a loop meant to clear field 13, but that loop iterates the outer wrapper instead of the nested `DamageParameter` rows, so it never changes a row. The Dynamite build that was actually played therefore kept all 146 flags.

Up to 0.10.33 this adapter walked the nested rows and really cleared the 146 flags, which diverged from the tested Dynamite behaviour. The clearing is now opt-in: `lua/coop/damage_parameters.lua` declares `local CLEAR_IGNORE_DEFENDER_FLAG = false`. With the default, the co-op table is a row-by-row copy equal to the original (`MgsCoopDamage.changedRows == 0`, `MgsCoopDamage.clearsIgnoreDefender == false`); activation still pairs the native opcode change with a table reload, and termination still restores the original table. Setting the constant to `true` restores the old clearing path for a recorded experiment (146 rows change). The default must stay `false` in shipped builds: the CTest checks below fail if the composed source changes any row.

This is a deliberate change to the no-`lab.ini` baseline (synthesis G15): a build from this source with no `lab.ini` no longer clears the 146 flags that the 0.10.33 loader cleared, although the loader version string is unchanged until the next release bump. To tell the two apart in live evidence, the activation receipt now names the loaded table. `MGS_COOP_DAMAGE_TABLE_ACTIVE_V1` is replaced by `return 'MGS_COOP_DAMAGE_TABLE_ACTIVE_V2' -- mode=parity;changed_rows=0`, or `-- mode=clear_field13;changed_rows=146` for the experiment. A 0.10.33 build emits the V1 receipt instead. The receipt reaches the script log only when the native observer logs that load (the first 32 script loads are always logged; logging every `MGS_COOP_DAMAGE_TABLE_` receipt needs a small native change that has not been made yet).

Checks (CTest, simulated engine APIs only): `damage_parameters_lua_check` runs the module on a synthetic table (parity default, opt-in experiment via source substitution, mode receipts, activation order, native refusal, reload errors, late activation); `damage_parameters_patch_check` composes the actual extracted table with the exact-source gate; `damage_parameters_composed_lua_check` executes that composition in Lua 5.1 and confirms 475 rows, 146 flags kept by default and exactly those 146 cleared by the experiment; when an upstream checkout is present (`work/upstream-dynamite`), it also executes Dynamite's own table and confirms that it reloads exactly the vanilla data. `damage_lifecycle_lua_check` covers the termination wrapper. Whether either setting lets both players damage enemies normally needs a live two-player run.
