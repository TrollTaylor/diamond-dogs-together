# Equipment-use restriction adaptation

Workspace 0.10.23 includes the mapped `UiControllerImplSetNoUseEquipId` adaptation from DYNAMITE `c90f252f8200765f66c005d6bf4357fda0c0d98e` (GPLv3 with Commons Clause 1.0). The hook substitutes ID 9999 and calls the original setter while the prepared co-op player rules are active, including pre-connection loading. Outside that scope it forwards all original arguments. Version 0.10.23 also adds the semantic current-build equivalent of `EquipCrossEvCallIsItemNoUse`, described below.

The exact 144-byte native setter is RVA `0xFE8320` in the fingerprinted 1.0.15.4 executable. Its two interface entries are `0x23AF550` and `0x23AF8C0`. RCX is the controller, DL the enable flag, and R8D the equipment ID. It obtains shared storage through the controller's interface at +0x48. Enabling inserts an ID into the first empty entry of a 32-dword restriction list at storage+0x1A4. Disabling clears matching IDs; ID zero clears all entries. Named Lua `SetNoUseEquipId` / `ResetNoUseEquipId` registrations point to implementations of these same storage operations. The initialization routine clears the list, and the equipment update scans it to clear selection when an ID matches.

The installer checks the complete setter and predicate bodies, a complete selection caller and both setter interface entries. It creates both hooks before enabling either, retains the original trampolines, and only enables either policy after both hooks install successfully. A partial installation forwards original behavior. It is connected to player preparation before the original `Mission.Start`. Existing player-rule cleanup disables the policy without removing a potentially executing trampoline. The hook does not retain controller pointers or issue independent game calls.

ID 9999 is DYNAMITE's sentinel policy, not proof of a universally unused ID. Enabling can insert duplicate sentinel entries; disabling during co-op clears sentinel entries rather than the original ID, including when the original request used zero. Those details intentionally match upstream. The adaptation does not retroactively clear preexisting restrictions, and turning the policy off does not reconstruct restrictions suppressed during co-op. Normal storage initialization remains game-owned. No item-use or scene-transition behavior has been verified in-game.

The additional predicate is RVA `0x8AE340`, 212 bytes. It receives selector RCX and equipment ID EDX, checks status masks via selector+0xE8, a flag at +0x2DE, an ID-specific condition for 0x1C3, and bit zero of the corresponding eight-entry item restriction flags at shared storage+0x98/+0xB8. Its AL result is a refusal: the complete 300-byte caller at 0x8AF040 branches to its return on true before switching selection indices +0x252/+0x253. Another instruction-boundary-verified direct call occurs at 0x8B2DA7. This is a semantic identification from dataflow and callers, not recovery of the stripped original symbol name.

During prepared co-op rules, the predicate hook calls the original then returns false, matching DYNAMITE's refusal bypass while preserving original execution. Outside that scope it returns the original result. It bypasses every refusal reason in this predicate, including general status and special-item checks; it is not restricted to an identified multiplayer-only bit. Other separate selection checks remain intact. This broad upstream policy needs gameplay assessment, especially in menus, special items and transitions. Neither hook retains game object pointers.
